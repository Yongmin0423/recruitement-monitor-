# 개인용 채용공고 모니터 기획·구현 계획

작성일: 2026-10-26

## 1. 목표와 결정 사항

내가 저장한 검색 조건으로 여러 채용 사이트의 최신순 목록을 주기적으로 확인하고, 새로 발견한 공고만 모아 보여주고 알림을 보낸다. 개인 비상업용으로 사용한다.

- 대상: 사람인, 잡코리아, 리멤버, 원티드, 링크드인.
- 화면: Next.js + TypeScript, Vercel Hobby에 배포.
- 백엔드: Cloudflare Workers Paid, D1, Cron Triggers.
- API를 이용할 수 있으면 사용하고, 개인 발급이 어렵거나 API가 없으면 공개 목록의 브라우저 수집을 검증한다.
- Browser Run으로 목록을 열고, 필요한 경우 Workers AI로 신규 공고의 목록 정보를 구조화한다.
- 상세 페이지는 수집하지 않는다. 자세한 내용은 원문 링크로 확인한다.
- 최초 일정은 평일 업무 시간 30분 간격, 저녁 2회, 수면 시간 중단, 주말 하루 3회다. 사이트별 호출 제한과 갱신 주기에 맞춰 조정한다.
- Wrangler는 개발·설정·배포 도구다. 수동 배포 또는 Git 연동 자동 배포를 사용할 수 있다.
- API 신청·승인이나 5곳 전체 연동을 기다리지 않고, 수집 가능한 한 사이트부터 완성한다.

## 3. 사이트별 사전 조사 결과

아래는 공식 공개 문서의 API 조사 결과다. API 키 발급과 실제 API 호출은 아직 검증하지 않았다. 공개 목록은 Cloudflare Browser Run에서 5곳 모두 소량 추출했다. 자세한 결과는 [수집 가능성 검증](feasibility.md)을 참조한다.

| 사이트 | 확인된 사실 | 구현 방향 |
|---|---|---|
| 사람인 | 승인형 채용 검색 API. 하루 최대 500회, 1회 최대 110건. 공식 무료 명시를 확인하지 못함 | 개인 이용·요금 확인 후 API 우선. 어려우면 공개 목록 수집 검증 |
| 잡코리아 | API 존재. 공공기관·학교 우선, 개인·기업은 내부 검토. 안내 갱신 주기 2시간. 요금 미명시 | 개인 승인과 갱신 주기 검토. 어려우면 공개 목록 수집 검증 |
| 원티드 | Jobs 목록 API 존재. 신청 화면에 사업자등록번호·회사명·서비스 URL 필수 표시. Jobs 무료 여부 미명시 | 개인 키 발급 가능 여부 확인. 어려우면 공개 목록 수집 검증 |
| 리멤버 | 외부 개발자용 공개 채용 검색 API 문서를 찾지 못함 | 공개 목록 수집 검증 |
| 링크드인 | 확인한 Job Posting API는 등록용. 개인용 공개 채용 검색 API 미확인 | Cloudflare 공개 검색 목록 수집 성공. 반복 안정성을 확인하고 불안정하면 보류 |

API가 공개되어 있다는 사실을 무료 이용 승인으로 해석하지 않는다. 개인용 무료 여부가 미확정인 API 비용은 예산에서 제외한 상태다. API 이용이 어려워도 전체 구현은 계속한다.

공개 검색 가능 여부와 자동 수집 허용·반복 접근 가능 여부는 별도로 확인한다. 제한을 우회하는 구현은 하지 않고, 지원할 수 없는 사이트는 상태와 이유를 표시한다. 웹사이트 내부 요청 주소를 공식 지원 API로 간주하지 않는다.

## 4. 수집 설계

### 4.1 방식 선택

사이트마다 다음 순서로 검증하고 가장 단순하고 안정적인 방식을 선택한다.

1. 이용 가능한 공식 API.
2. HTTP 응답의 목록 HTML에서 직접 추출.
3. Browser Run으로 렌더링한 목록 요소에서 추출.
4. 신규 목록 항목을 Workers AI로 구조화.

목록을 읽는 것과 LLM으로 분석하는 것은 별도 단계다. 신규 여부를 알기 위해 매번 전체 목록을 LLM에 보내지 않는 것이 기본 원칙이다.

### 4.2 실행 흐름

```text
Cron → 실행할 사이트·검색 조건 선택
  → 검색 조건에 해당하는 최신순 목록 조회
  → 코드로 공고 ID·원문 링크 추출
  → D1의 기존 공고와 비교
  → 처음 발견한 공고의 목록 카드 정보 확보
  → 코드 추출 또는 필요한 경우 Workers AI 구조화
  → 결과 검증 및 저장
  → 개인 필터 매칭
  → 알림 대기 기록 생성
  → 웹 푸시 발송·결과 기록
```

예: 이전 목록이 A·B·C이고 현재 목록이 F·E·A·B·C이면 F·E만 새 공고로 처리한다.

### 4.3 탐색과 중복 규칙

- 공고 식별자는 `source + source_job_id`. ID가 없으면 추적 매개변수 등을 정리한 원문 URL을 사용한다.
- 제목만으로 동일 공고를 판정하지 않는다.
- 광고·고정 공고·재등록 때문에 기존 공고 하나를 만났다고 즉시 종료하지 않는다.
- 최근 확인 구간과 겹치게 탐색하고, 사이트별 정렬 특성을 검증한 뒤 연속 기존 공고 구간 등을 종료 조건으로 사용한다.
- 정렬이 불안정하면 제한된 범위의 주기적 재확인을 병행한다.
- 최대 페이지 수에 도달하면 수집 범위 제한 상태를 기록한다. 전체를 확인했다고 표시하지 않는다.
- 첫 실행은 기존 공고를 저장만 하고 알림을 보내지 않는다.
- 검색 조건을 새로 추가할 때도 초기 데이터의 알림 여부를 명시적으로 처리한다.
- 동일 ID의 단순 수정은 신규 알림을 보내지 않는다. 재등록에 따른 새 ID는 별도 공고로 기록한다.
- 다른 사이트의 유사 공고는 초기에는 각각 보관한다.
- 목록에서 사라졌다는 이유만으로 마감이라고 판단하지 않는다.
- 원본 게시 시각이 없으면 최초 발견 시각만 표시하고, 이를 게시 시각으로 표현하지 않는다.

### 4.4 AI 추출 규칙

- 입력은 신규 공고 카드의 텍스트 중심으로 제한한다. 스크린샷 분석은 필요성이 확인될 때만 검토한다.
- 제목·회사 원문을 보존하고, 지역·경력은 표시된 내용만 구조화한다.
- 없는 정보는 null로 반환한다. 제목으로 지역·경력을 추측하지 않는다.
- JSON 스키마로 검증하고, 공고 링크는 원본 목록에서 확보한 값과 대조한다.
- 웹페이지의 문구는 데이터로 취급한다. 페이지 내 지시문을 실행하거나 따르지 않는다.
- AI 실패 시 공고 ID·링크·원문 카드 텍스트는 보관해 제한된 횟수로 재처리한다.
- ID·링크 선추출이 불가능한 사이트는 예외로 분리하고 전체 목록 분석 비용을 별도 측정한다.

### 4.5 시간대별 수집 주기

한국시간(KST) 기준, 사이트 5곳과 검색 조건 1개로 시작한다.

| 시간대 | 실행 시각 | 목적 |
| --- | --- | --- |
| 평일 오전 | 08:00 1회 | 밤사이 신규 공고 따라잡기 |
| 평일 업무 시간 | 09:00~17:00, 1시간 간격 | 신규 공고 빠르게 확인 |
| 평일 저녁 | 19:00, 21:00 | 퇴근 후 공고를 느린 주기로 확인 |
| 평일 21:00~다음날 08:00 | 실행 없음 | 수면 시간에는 수집과 알림 중단 |
| 주말 | 10:00, 16:00, 22:00 | 6~12시간 간격으로 확인 |

Cloudflare Cron은 매 정시에 Worker를 깨우되, 실제 Browser Run 실행 여부는 Worker에서 KST로 계산한다. 사용자가 화면에 들어올 때는 마지막 성공 수집이 30분 이상 지난 활성 조건만 백그라운드로 확인한다. 동일 조건의 중복 실행은 Worker 잠금과 재확인으로 막는다. 쉬는 시간의 Cron 호출은 목록 페이지를 열지 않는다. 첫 실행은 사이트별 2~5분씩 분산해 순간 동시 실행을 줄인다.

긴 공백 뒤 첫 실행은 최신순 목록을 최대 3페이지까지 확인한다. 공고 ID와 이미 저장된 구간의 겹침을 확인하되 광고·고정 공고 때문에 기존 ID 하나만 보고 멈추지 않는다. 페이지 상한에 닿아도 기존 구간을 찾지 못하면 수집 범위 부족을 기록하고 다음 실행에서 계속 확인한다. 알림은 발견 시점에 보내므로 밤에 게시된 공고는 다음 실행까지 늦어진다. 정상 수집과 충분한 페이지 범위라는 조건에서 최장 지연은 금요일 21:00 이후부터 토요일 10:00 전까지 약 13시간이다.
## 5. 아키텍처와 저장 구조

```text
Vercel: Next.js UI + 개인 로그인
           ↓ 인증된 서버 간 요청
Cloudflare: Web API Worker ↔ D1
                              ↑
            Cron → Collector Worker
                     ├ API / HTTP / Browser Run
                     ├ Workers AI
                     └ 알림 처리
```

브라우저에 Cloudflare 관리 토큰이나 LLM 키를 노출하지 않는다. Next.js의 서버 측 요청에서도 사용자 인증을 확인하고 Worker API도 인증한다. 공개 회원가입 없이 본인 계정만 허용한다.

한 저장소에서 웹앱, Worker, 공통 타입을 관리한다. 웹앱 요청 안에서 여러 사이트 수집을 끝까지 기다리게 하지 않는다. 긴 작업은 사이트·검색 단위로 분리하고, 실행 제한이나 재시도 관리가 필요해지면 Cloudflare Queues를 추가한다.

| 테이블 | 용도 |
|---|---|
| searches | 키워드, 지역, 경력, 미기재 포함 등 개인 조건 |
| source_searches | 사이트별 검색 매핑, URL, 주기, 실행 예정 시각, 활성화 |
| jobs | 출처·ID·원문 URL·목록 정보·최초/최근 발견 시각 |
| job_matches | 검색 조건과 공고 연결, 최초 매칭 시각 |
| job_states | 읽음·관심·숨김 |
| collection_runs | 실행 결과, 페이지 수, 신규 수, 오류, 브라우저 시간·토큰 |
| notifications | 발송 대기·성공·실패, 재시도 횟수, 중복 방지 키 |
| push_subscriptions | 본인 기기의 웹 푸시 구독 |

`jobs`의 출처·공고 ID와 `notifications`의 중복 방지 키에 고유 제약을 둔다. 수집 실행은 사이트·검색 단위의 만료 가능한 잠금으로 겹침을 방지한다. 알림은 저장된 대기 기록을 기반으로 발송하며, 네트워크 응답 유실에 대비해 클라이언트에서도 가능한 범위의 중복 제거를 적용한다.

## 6. 비용 산정

### 6.1 공식 요금 기준

- Vercel Hobby: 개인 비상업용, 포함 한도 내 $0.
- Workers Paid: 월 기본 $5, 초과 사용량 별도.
- D1: 포함 사용량 내 추가 비용 없음.
- Browser Run Paid: 월 10시간 포함, 초과 시간당 $0.09. 세션 방식은 동시성 요금 조건도 있으므로 낮은 동시성으로 운영한다.
- Workers AI: Free·Paid 모두 하루 10,000 Neurons 무료. Paid 초과량은 1,000 Neurons당 $0.011.
- AI 무료량은 매일 UTC 00:00, 한국 시간 09:00 초기화된다. 월 단위 이월 크레딧으로 계산하지 않는다.
- Workers 구독료가 AI 토큰 잔액으로 바뀌는 것은 아니다. 외부 LLM 업체를 직접 호출하면 그 업체 요금이 별도 적용된다.

### 6.2 브라우저 비용 가정

시간대별 일정의 30일 예시: 평일 22일, 주말 8일, 사이트 5곳, 검색 조건 1개.

- 평일 사이트당 08:00 1회 + 업무 시간 9회 + 저녁 2회 = 12회/일.
- 주말 사이트당 3회/일.
- 월 기본 조회는 (22일 × 12회 + 8일 × 3회) × 5곳 = **1,440페이지**.
- 매일 첫 조회에서 2페이지를 추가로 확인하는 예시는 **1,740페이지**다. 다른 정기 확인에서 신규 공고가 많아 2~3페이지를 읽거나 접속 시 추가 확인이 발생하면 실제 페이지 수는 더 늘어난다.

| 페이지당 브라우저 시간 | 월 브라우저 시간 (1,440~1,740페이지 예시) | Paid 포함 10시간 초과 비용 |
| --- | ---: | ---: |
| 7.2초 (소량 테스트의 반올림된 평균) | 2.88~3.48시간 | $0 |
| 10초 | 4.00~4.83시간 | $0 |
| 20초 | 8.00~9.67시간 | $0 |
| 30초 | 12.00~14.50시간 | 약 $0.18~0.41 |

이번 10회 소량 검증의 누적 표시값은 0.02시간이다. 이를 요청당 약 7.2초로 환산한 값은 운영 환경의 확정 평균이 아니다. 다른 Cloudflare 서비스가 같은 Browser Run 월 10시간을 사용한다면 여유가 줄어든다. 검색 조건, 페이지 수, 재시도, 대기 시간이 늘어나면 실제 비용도 증가한다. 사이트별 시간을 기록해 주기를 다시 조정한다.
### 6.3 신규 공고 AI 비용 가정

비교용 모델: `@cf/meta/llama-3.3-70b-instruct-fp8-fast`.

- 입력 100만 토큰당 $0.293, 출력 100만 토큰당 $2.253.
- 공고당 입력 300토큰, 출력 150토큰 가정. 입력에는 프롬프트 비용을 포함하거나 묶음 처리 시 배분해야 한다.
- 무료량 차감 전 공고당 약 $0.000426.
- 이 가정에서는 무료량이 대략 하루 250건의 분석에 해당한다. 실제로는 모델·토큰·계정의 다른 AI 사용량에 따라 달라진다.

| 일정한 일일 분석량 | 무료량 적용 후 예상 AI 비용 |
|---|---:|
| 30건 | $0 |
| 100건 | $0 |
| 200건 | $0 |
| 약 333건, 월 약 1만 건 | 월 약 $1 |

일별로 고르게 발생하고 다른 작업이 무료량을 소모하지 않는 가정이다. 특정 날 몰리면 같은 월 공고 수라도 요금이 달라진다. 모델의 한국어 추출 정확도는 미검증이며 채택은 실험 후 결정한다.

### 6.4 운영 예산

하루 AI 분석 200건 이내, 위 브라우저 사용량, 다른 자원은 포함 한도 이내라는 조건:

- 구독료 포함 예상: 월 $5.00~6.15.
- Workers를 이미 구독하고 있다면 이 도구로 인한 브라우저 추가 지출: 월 $0~1.15 예상.
- 초기 예산 목표: 구독료 포함 월 $15.

세금, 환율, 별도 도메인, 유료 채용 API, 유료 알림 업체는 제외했다. 기본 배포 도메인과 직접 구현한 웹 푸시를 사용한다. 동일 계정의 다른 서비스가 포함량을 사용한다면 재계산한다.

이 예산은 보장된 청구 상한이 아니다. 일일 AI 사용량·브라우저 시간·최대 페이지·재시도·토큰 수를 제한하고, 예산 접근 시 수집 간격을 늘리거나 AI 처리를 중단하는 동작을 구현한다.

## 구현 반영 메모 (2026-10-26)

현재 바탕화면 프로젝트에는 Next.js 화면, 로컬 D1, 사람인 수집기가 구현되어 있다. 신규 검색 조건은 등록일 기준 최근 30일의 열려 있는 공고를 3페이지씩 이어서 백필하고, 완료 후에는 평소 최신 1페이지, 아침 최대 3페이지를 확인한다. 목록에 `수정일`만 표시된 공고는 최초 등록일을 알 수 없어 30일 조건에서 제외한다. 초기 기준 데이터는 새 공고 알림 대상이 아니다. 로컬 검증에서 `프론트엔드` 검색 34페이지를 읽어 조건에 맞는 공고 654건을 표시했다. 이 초기 백필은 기존 정기 확인 비용 산정에 포함되지 않은 일회성 추가 요청이며, 검색 조건당 실제 읽은 페이지 수를 비용 기록에 더해야 한다. 잡코리아·리멤버·원티드·링크드인 수집기, 푸시 알림, 원격 배포는 아직 남아 있다.


수집 주기 변경(2026-10-26): 평일 업무 시간은 1시간 간격으로 줄이고, 화면 첫 진입 시 30분 이상 지난 검색만 조건부로 확인한다. 최신 수집은 기존 적격 공고 10개 연속 겹침을 확인하거나 최대 3페이지에서 멈춘다. 기본 비용 예시에는 접속 시 추가 요청과 페이지 겹침 확인에 따른 추가 페이지가 포함되지 않는다.
